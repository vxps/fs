# Эксперимент H1 — конкурентное бронирование

## Гипотеза

Паттерн **preclaim** (короткая транзакция-блокировка → оплата вне транзакции → короткая транзакция-подтверждение) устраняет неопределённые состояния (`unsafe_abort`) при параллельных бронированиях по сравнению с контрольным контуром, где оплата выполняется внутри основной транзакции.

## Дизайн эксперимента

- **СУБД:** PostgreSQL с ограничением `EXCLUDE USING gist` на пересечение временных интервалов (`tstzrange`).
- **Контуры:**
  - `control` — оплата внутри транзакции (удерживает блокировку на всё время оплаты).
  - `preclaim` — claim (короткая TX) → оплата (вне TX) → confirm (короткая TX). При неудаче — компенсирующий откат.
- **Сетка параметров:** 5 × 5 = 25 ячеек.
  - Уровни конкуренции: C ∈ {1, 2, 5, 10, 25} параллельных запросов.
  - Задержка оплаты: D ∈ {0, 100, 500, 1000, 2000} мс.
- **Повторения:** 20 раундов на ячейку → 8 600 измерений.

## Файлы

| Файл | Описание |

## Основные результаты

- **Preclaim: 0 `unsafe_abort`** из 4 300 попыток (все уровни C и D).
- **Control: ~10% `unsafe_abort`** при C ≥ 2 (431 из 4 300).
- Fisher exact test: p < 10⁻⁵ для C ≥ 2 — разность статистически значима.
- Ветка компенсации (`preclaim`) выполнялась 53 раза (0.6% попыток) — откаты работают корректно.

## Запуск

```bash
pip install -r requirements.txt

# 1. Создать БД и схему
psql -d fitspot_experiment -f schema.sql

# 2. Запустить эксперимент (настроить DSN через переменную окружения)
export FITSPOT_EXPERIMENT_DSN="host=127.0.0.1 port=5432 user=postgres dbname=fitspot_experiment"
python experiment.py

# 3. Анализ
python analyze.py
```
